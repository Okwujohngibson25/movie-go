# Backend Architecture & Conventions

How I build Go REST backends, taken from a reference codebase. Snippets use a generic `Item` entity, and file paths point to the real examples. Anything marked **[INFERRED]** was concluded rather than seen directly. **Inconsistent:** marks places where the code doesn't agree with itself. **Canonical:** is the rule new code must follow in those places, and it wins over whatever the reference code does.

## 2. Project structure

```
cmd/api/main.go            # composition root: config → pool → repos → services → handlers → routes
migrations/<ts>_<name>.sql # goose migrations; also the sqlc schema source
db/queries/<entity>.sql    # sqlc query files, one per table
sqlc.yaml                  # generates into internal/database/db
api/<area>/<feature>/*.http# hand-written request samples, one per endpoint (gitignored)
internal/
  <feature>/               # one package per business feature
    handler.go dto.go input.go mapper.go service.go
  domains/                 # plain shared structs, one file per entity
  postgres/<entity>.go     # repository implementations over sqlc
  database/postgres.go     # pgxpool connect + ping
  database/db/             # GENERATED by sqlc. Never edit by hand.
  apperrors/  response/  middleware/  validation/  config/  helper/
```

Business code is packaged **by feature** and infrastructure by concern. All repository implementations share one `internal/postgres` package rather than living inside each feature.

**Adding a feature:**
1. Write a migration with `goose -dir migrations create <name> sql`, then run it up. **[INFERRED]** that `goose create` is used, based on the `20260913085404_` timestamp prefixes.
2. Add queries to `db/queries/<entity>.sql` and run `sqlc generate`.
3. Add a domain struct in `internal/domains/<entity>.go`.
4. Add `internal/postgres/<entity>.go` with `New<Entity>SqlcRepository(pool)`.
5. Create `internal/<feature>/` with `service.go` (which declares the repository interface), `input.go`, `dto.go`, `mapper.go` and `handler.go`.
6. Add sentinel errors and their `case` in `internal/apperrors/errors.go`.
7. Wire repo → service → handler and register the routes in `cmd/api/main.go`.
8. Add `.http` samples under `api/`.

A placeholder feature can start out as empty files (`internal/booking/*.go`).

## 3. Architecture and layering

```
chi route → middleware → handler → service → repository (internal/postgres) → sqlc Queries → Postgres
```

| Layer | Responsibility | Types it works with | Example |
|---|---|---|---|
| handler | decode JSON, validate, parse path params, map DTO→Input, call service, write envelope | `dto.go` request/response DTOs, `input.go` | `internal/movie/handler.go`, `internal/screen/handler.go` |
| service | business rules, generate IDs, normalize input, derived fields, hash passwords | `XInput` in, `domains.X` out | `internal/movie/service.go`, `internal/showing/service.go` |
| repository | domain ↔ `pgtype` conversion, DB error → sentinel translation, transactions | `domains.X`, sqlc params/rows | `internal/postgres/movie.go`, `internal/postgres/screen.go` |
| sqlc | generated query methods | `db.*Params`, `db.*Row` | `internal/database/db/` |

Each layer keeps its own types. `pgtype` and sqlc types stay inside `internal/postgres`, and JSON/`validate` tags appear only on DTOs.

**Dependency injection** is manual, through constructors. There are no globals and no framework.

```go
// cmd/api/main.go
itemRepo := postgres.NewItemSqlcRepository(pool)
itemService := item.NewItemService(itemRepo)
itemHandler := item.NewItemHandler(itemService, validate)
```

**Consumer-side interfaces.** Each service declares the repository interface it needs. When it needs another feature's data, it declares a narrow interface and receives that feature's *repo*, not its service.

```go
// internal/showing/service.go
type Movie interface { // narrow, cross-feature
	FindMovieByID(ctx context.Context, id uuid.UUID) (domains.Movie, error)
}
func NewShowingService(repo ShowingRepository, movie Movie) *ShowingService
```

Services hold the interface type. Handlers hold the concrete `*XService`.

## 4. API conventions

- **Versioning** is by URL prefix: everything sits under `/api/v1`, in nested `r.Route` blocks per area (`/auth`, `/admin`). See `cmd/api/main.go`.
- **Resources** are plural nouns (`/items`, `/items/{itemID}`), and sub-resources are nested (`/screens/{screensID}/seats`). **Inconsistent:** path params are usually `{<singular>ID}`, but one feature uses the plural `{screensID}`.
- **Methods**: `GET` for list and get, `POST` to create, `PUT` for a full update, `DELETE` to delete. There's no `PATCH`.
- **Status codes**: 201 on create, 200 on read/update/delete (delete returns a body, not 204), 400 for validation/JSON/bad ID, 401 for missing or invalid token and bad login, 403 for wrong role, 404 for not found, 409 for a duplicate, 500 otherwise. **Inconsistent:** body-too-large returns 409 instead of 413 (`internal/apperrors/errors.go:60`). **Canonical:** body-too-large is `413 Request Entity Too Large` (`http.StatusRequestEntityTooLarge`), and 409 is reserved for duplicates and conflicts.
- **JSON keys** are `snake_case` (`start_time`, `screen_id`).
- **Pagination, filtering and sorting** aren't implemented. List endpoints return everything.
- **The envelope is the same for every success and error response** (`internal/response/response.go`):

```go
type APIResponse[T any] struct {
	Code    string         `json:"code"`              // SCREAMING_SNAKE
	Message string         `json:"message"`
	Data    T              `json:"data,omitempty"`
	Details []ErrorDetails `json:"details,omitempty"` // validation errors: {field, message}
}
response.WriteJSON(w, http.StatusOK, response.APIResponse[any]{Code: "ITEMS_FETCHED", Message: "items fetched successfully", Data: toItemResponse(items)})
```

Create/update/delete responses carry no `data`; they don't echo the resource back.

**Inconsistent:** success codes vary in style (`MOVIES_FETCHED`, `MOVIE_CREATED_SUCCESSFULLY`, `FETCHED_ALL_SHOWINGS_SUCCESSFULLY`), and so does message capitalization. `<ENTITY>_<VERB>ED[_SUCCESSFULLY]` is the most common form.

**Canonical success codes:** `<ENTITY>_<PAST_TENSE_VERB>`, with no `_SUCCESSFULLY` suffix. The entity is singular for single-item operations and plural for lists. Messages are lowercase sentences.

| Operation | Code | Message |
|---|---|---|
| list | `ITEMS_FETCHED` | `items fetched successfully` |
| get one | `ITEM_FETCHED` | `item fetched successfully` |
| create | `ITEM_CREATED` | `item created successfully` |
| update | `ITEM_UPDATED` | `item updated successfully` |
| delete | `ITEM_DELETED` | `item deleted successfully` |
| login | `LOGGED_IN` | `logged in successfully` |

**Request decoding** always goes through `helper.DecodeJSON` (`internal/helper/json.go`). It enforces a 1 MiB `MaxBytesReader`, `DisallowUnknownFields`, and a single JSON value with no trailing data.

## 5. Validation

- Validation happens in the **handler**, right after decoding, against the request DTO's struct tags: `if err := h.validate.Struct(req); err != nil { apperrors.HandleError(w, err); return }`.
- One shared `*validator.Validate` is built in `validation.NewValidator()`, injected into handlers, and holds the custom tags. A registration error panics at startup.

```go
// internal/validation/validator.go
v.RegisterValidation("rating", func(fl validator.FieldLevel) bool { /* decimal in [1,5] */ })
// dto.go
Rating decimal.Decimal `json:"rating" validate:"required,rating"`
Password string        `json:"password" validate:"required,min=8,max=16"`
```

- `validator.ValidationErrors` is converted by `HandleError` into a 400 with `VALIDATION_ERROR`, where each `details[]` entry is `{field: <Go field name>, message: <tag>}`.
- UUID path params are checked with `uuid.Parse` and return `apperrors.ErrInvalidID` on failure (`internal/movie/handler.go`).
- **Inconsistent:** `internal/showing/handler.go` has no validator and no `validate` tags. It takes IDs as strings and parses them by hand. The tagged-DTO approach is the more common one.
- **Canonical:** every handler that decodes a body injects `validate` and calls `validate.Struct(req)`, with no exceptions. Every request DTO field gets a `validate` tag. UUIDs in a body are strings tagged `validate:"required,uuid"`, then converted with `uuid.Parse` when mapping to `XInput`.

```go
type CreateItemRequest struct {
	ParentID  string    `json:"parent_id" validate:"required,uuid"`
	StartTime time.Time `json:"start_time" validate:"required"`
}
```

## 6. Auth and authorization

- **Register/login** are public routes (`POST /api/v1/auth/register`, `/login`). Emails are normalized with `strings.ToLower(strings.TrimSpace(...))`.
- **Password hashing**: `bcrypt.GenerateFromPassword(pw, 10)`, checked with `bcrypt.CompareHashAndPassword` (`internal/user/service.go`).
- **Login failures** all return the same `ErrInvalidLoginCredentials`, so the response doesn't reveal whether an email exists.
- **Tokens** are JWT HS256 signed with `JWT_SECRET`. The access token lasts 15 minutes and goes in `data`. The refresh token lasts 7 days and is set as an `HttpOnly; Secure` cookie named `refresh_token`. Claims carry `typ: "access" | "refresh"`. There's no refresh endpoint yet, and sessions are stateless (no server-side store).
- **Authentication middleware** (`internal/middleware/authentication.go`):
  - It reads the raw token from `Authorization`, with **no `Bearer ` prefix**.
  - It requires an HMAC signing method and rejects any token whose `typ` isn't `access`.
  - It stores the claims in the context under an unexported `contextKey` type.
- **Authorization** is role-based middleware stacked on a route group. There are no ownership checks yet.

```go
r.Group(func(r chi.Router) {
	r.Use(middleware.RequireAuth(cfg.App.JWTSecret))
	r.Use(middleware.RequireAdmin) // claims.Role != "admin" → ErrUnauthorized (403)
	...
})
```

- **Inconsistent:** the claims struct is defined twice, once for signing (`user.CustomClaims`, untagged) and once for parsing (`middleware.CustomClaims`, tagged). They only match because Go's JSON decoding is case-insensitive.
- **Canonical:** define one claims struct in `internal/auth`, with explicit lowercase JSON tags on every field. Both token signing and middleware parsing import it, and handlers read claims through `auth.ClaimsFromContext(ctx)`. Never redeclare claims anywhere else.

```go
// internal/auth/claims.go
type Claims struct {
	UserID uuid.UUID `json:"user_id"`
	Email  string    `json:"email"`
	Role   string    `json:"role"`
	Type   string    `json:"typ"` // "access" | "refresh"
	jwt.RegisteredClaims
}
```
- The admin account is seeded at startup from env vars if it doesn't already exist (`UserService.SeedAdmin`).

## 7. Database

- **Naming**: tables are plural `snake_case` (`users`, `booking_seats`), and so are columns. Foreign keys are `<entity>_id UUID NOT NULL REFERENCES <table>(id)`.
- **IDs**: `id UUID PRIMARY KEY` with **no DB default**. They're generated in the service with `uuid.New()`.
- **Timestamps**: `created_at TIMESTAMPTZ NOT NULL DEFAULT now()` on most tables. There's no `updated_at`. **Inconsistent:** some tables have no `created_at` at all (`migrations/20260913173722_screens_table.sql`). sqlc maps `timestamptz` to `time.Time`, or `*time.Time` when nullable (`sqlc.yaml`).
- **Soft delete**: a `deleted_at TIMESTAMPTZ` column. Every read and update filters `AND deleted_at IS NULL`, and delete is `UPDATE ... SET deleted_at = now()` (`db/queries/movies.sql`). Only one table uses it so far.
- **Enums** are Postgres enums: `CREATE TYPE account_role AS ENUM ('user','admin')`. In Go they're a `string` in the domain, converted to and from the sqlc type (`db.AccountRole(...)`) in the repo.
- **Decimals** are `NUMERIC(p,s)` ↔ `decimal.Decimal`. Writes use `pgtype.Numeric.Scan(d.String())`, and reads use `helper.NumericToDecimal`, which errors on NULL/NaN/Inf. Nothing stores money yet. **[INFERRED]** money would follow the same pattern.
- **Migrations** use goose, one table per file, with `Up` and `Down` both wrapped in `StatementBegin/End`. `Down` uses `DROP ... IF EXISTS` (`migrations/20260913085404_create_users_table.sql`).
- **Queries** (`db/queries/*.sql`):
  - Names are PascalCase verbs: `CreateX`, `GetAllX`, `FindXByID`, `UpdateXByID`, `DeleteXByID`.
  - Reads select explicit columns.
  - Updates and deletes use `:execrows`, so the repo can turn 0 affected rows into "not found".
  - Joined columns get aliases (`m.title AS movie_title`).
- **Duplicate handling**: either `ON CONFLICT DO NOTHING RETURNING *` (so `pgx.ErrNoRows` means "exists"; see `db/queries/movies.sql`) or checking `*pgconn.PgError` code `23505` (`internal/postgres/user.go`). Both appear.
  **Canonical:** use plain `INSERT` (no `ON CONFLICT DO NOTHING`) and translate unique violations in the repository. This catches every unique constraint, including ones added later, and keeps `pgx.ErrNoRows` meaning only "not found".

```go
var pgErr *pgconn.PgError
if errors.As(err, &pgErr) && pgErr.Code == "23505" {
	return apperrors.ErrItemAlreadyExists // and add its 409 case in HandleError
}
```
- **Transactions** live in the repository, which keeps the pool alongside the queries:

```go
// internal/postgres/screen.go
tx, err := r.db.Begin(ctx); if err != nil { return err }
defer tx.Rollback(ctx)
q := r.queries.WithTx(tx)
// ... q.CreateX(ctx, ...)
return tx.Commit(ctx)
```

- **Seeding** happens only in code, at startup. There are no seed SQL files.

## 8. Error handling and logging

- **Sentinel errors** all live in one `var (...)` block in `internal/apperrors/errors.go`, e.g. `ErrItemNotFound = errors.New("item not found")`. There are no custom error types or classes.
- **Repositories translate** DB outcomes into sentinels: `pgx.ErrNoRows` → `ErrXNotFound`, 0 rows → `ErrXNotFound`, `23505` → `ErrXAlreadyExists`. Services pass errors through unchanged or wrap them with `fmt.Errorf("failed to ...: %w", err)` (`internal/user/service.go`).
- **One global mapper**: `apperrors.HandleError(w, err)` is the only code that turns an error into a response. It's a `switch` over `errors.As`/`errors.Is`, one case per sentinel. Anything unmatched is logged with `log.Printf("internal error: %v", err)` and returned as a generic 500. A new sentinel needs a new `case`, or it falls through to 500.
- **Handlers** always follow this shape: `if err != nil { apperrors.HandleError(w, err); return }`.
- **Logging** is unstructured stdlib `log`. It logs startup and seeding status, unmapped errors, and signing failures. There's no request logging, request IDs, or panic-recovery middleware. **Inconsistent:** there's stray `fmt.Printf` debugging in a handler (`internal/movie/handler.go:36`) and `fmt.Println` in `internal/database/postgres.go`.

## 9. Config and secrets

- There's one typed `Config` with nested sub-structs, loaded once in `main` and passed down as `*config.Config`. Nothing else calls `os.Getenv`.

```go
// internal/config/config.go
type Config struct { App AppConfig; Database DatabaseConfig }
func LoadConfig() (*Config, error) { if err := godotenv.Load(); err != nil { return nil, err } ... }
```

- Keys are `PORT` (including the colon, e.g. `:8080`), `APP_ENV`, `JWT_SECRET`, `DATABASE_URL`, `Admin_email` and `Admin_Password`. **Inconsistent:** the key casing is mixed; `UPPER_SNAKE` is the majority. **Canonical:** every env key is `UPPER_SNAKE_CASE` (e.g. `ADMIN_EMAIL`, `ADMIN_PASSWORD`), and `.env.example` lists every key the config reads.
- `.env` is gitignored and `.env.example` is committed.
- A missing `.env` is fatal. Required values aren't validated beyond that.
- `APP_ENV` is loaded but never read. There's no per-environment behavior.

## 12. Testing

- **Framework**: stdlib `testing` with `httptest`. There's no testify, gomock, or testcontainers.
- **Layout**: `*_test.go` files sit next to the code, in the **same package** (white-box), so tests can reach unexported helpers like `movieFromRow` and `claimsKey`.
- **Test types**:
  - Unit tests for helpers (`internal/helper/decode_test.go`).
  - Middleware tests via `httptest.NewRecorder` (`internal/middleware/authentication_test.go`).
  - Service tests with hand-written fakes of the consumer-side interface (`internal/user/service_test.go`).
  - Repository row-mapping tests that need no DB (`internal/postgres/movie_test.go`).
- **No database in tests yet.** Repository tests against a real Postgres are planned but not written.
- **Patterns**:
  - Table-driven `tests := []struct{ name ... }` with `t.Run`.
  - Helpers that call `t.Helper()`.
  - `t.Cleanup` to restore global state.
  - A `const testSecret` in each package.
  - `bcrypt.MinCost` in tests.
  - Asserting on the response `code` string as well as the status.

```go
// fake repo: records calls, returns configured errors
type fakeRepo struct { item domains.Item; findErr, createErr error; created []domains.Item }
func (f *fakeRepo) Create(ctx context.Context, d domains.Item) error { f.created = append(f.created, d); return f.createErr }
```

- **Naming**: `TestThing_ExpectedBehavior` (e.g. `TestSeedAdmin_SkipsWhenCredentialsMissing`). Failure messages read `got X, want Y`.
- **Running**: `go test ./...`. For a single test, `go test ./internal/<pkg> -run TestName`.

## 13. Code style

- **Files**: lowercase, fixed names per feature package (`handler.go`, `service.go`, `dto.go`, `input.go`, `mapper.go`). Repo files are named after the entity (`postgres/<entity>.go`).
- **Types**: `XHandler`, `XService`, `XRepository` (interface), `XSqlcRepository` (impl), `CreateXRequest`/`UpdateXRequest`, `XResponseDTO`, `XInput`. **Inconsistent:**
  - Some request DTOs are named `CreateXDTO` (`internal/showing/dto.go`).
  - Some features share one `XInput` for create and update, while others have `CreateXInput`/`UpdateXInput`.
- **Canonical DTO names:** `CreateXRequest` / `UpdateXRequest` for request bodies and `XResponse` for response bodies. Never use a `DTO` suffix.
- **Constructors**: `NewXHandler`, `NewXService`, `NewXSqlcRepository`, each returning a pointer.
- **Methods** repeat the entity name: `GetAllItems`, `GetItemByID`, `UpdateItemByID`, `DeleteItemByID`.
- **Mappers**: `toXResponse([]domains.X)` for lists and `toSingleXResponse(domains.X)` for one item (`internal/movie/mapper.go`).
- **Receivers** are **inconsistent**: handlers use `s` or `h`, services use `r` or `s`, and repos always use `r`. **Canonical:** `h` for handlers, `s` for services, `r` for repositories, the same on every method of a type.
- **Slices** are preallocated with `make([]T, 0, len(src))`, which also means JSON gets `[]` instead of `null`.
- **Context**: every handler passes `r.Context()` into the service, and every repo method takes `ctx` first. There's no goroutine or channel use; everything runs synchronously in the request goroutine.
- **Imports**: stdlib first, then a blank line, then module-internal and third-party mixed in one alphabetical group (goimports default).
- **Comments** are sparse. Short `// why` notes go on non-obvious lines; exported identifiers have no doc comments.
- **Formatting** is `gofmt`. There's no linter config.

## 14. Tooling and workflow

- **Module management**: Go modules. There's no Makefile, Docker, docker-compose, CI config, or pre-commit hooks.
- **Commands**:
  - `air`: hot reload (`.air.toml` builds `./cmd/api` into `./tmp/main`).
  - `go run ./cmd/api`
  - `sqlc generate`
  - `goose -dir migrations postgres "$DATABASE_URL" up`
  - `go build ./... && go vet ./... && go test ./...`: the pre-review gate.
- **Manual API testing** uses `.http` files under `api/`, one per endpoint.
- **AI-assisted workflow** (from `CLAUDE.md` and `.claude/`):
  - Tasks are tracked in `docs/TASKS.md`, with statuses `todo → tests-review → in-progress → code-review → done`.
  - Development is test-first with approval gates.
  - A `.claude/hooks/protect-tests.sh` pre-edit hook blocks changes to `_test.go` files while a task is `in-progress`.
- **Branches**: `<id>-<short-title>` (`t0-refresh-token`), cut from `main`.
- **Commits**: `task <id>: <title>` for task work. Other commits use Conventional Commits (`feat(api): ...`, `fix: ...`).

## 15. Rules for new code (for an AI assistant)

**Do:**
- Package business code by feature: `internal/<feature>/{handler,service,dto,input,mapper}.go`. Put repositories in `internal/postgres/<entity>.go`.
- Declare the repository interface inside the service that uses it. For cross-feature reads, declare a one-method interface and inject the other feature's repo.
- Wire every dependency by hand in `cmd/api/main.go` using `NewX(...)` constructors, in the order repo → service → handler.
- In handlers, follow this order: `helper.DecodeJSON` → `validate.Struct` → `uuid.Parse` path params (`ErrInvalidID`) → map to `XInput` → call service → `response.WriteJSON` with `APIResponse[any]`. Always `return` right after `HandleError`.
- Generate IDs with `uuid.New()` in the service. Normalize emails and similar strings in the service.
- Keep `pgtype`/sqlc types inside `internal/postgres`. Translate `pgx.ErrNoRows`, 0 rows from `:execrows`, and `23505` into sentinels there.
- Use `:execrows` for updates and deletes. Select explicit columns. Filter `deleted_at IS NULL` on soft-deleted tables.
- Run multi-statement writes in a repo-level transaction: `Begin` / `defer Rollback` / `WithTx` / `Commit`.
- Add each new sentinel to `apperrors` **and** add its `case` in `HandleError` in the same change.
- Store decimals as `NUMERIC` ↔ `decimal.Decimal`, timestamps as `TIMESTAMPTZ` ↔ `time.Time`, and fixed sets as Postgres enums.
- Use receivers `h` (handler), `s` (service) and `r` (repository).
- Name request DTOs `CreateXRequest`/`UpdateXRequest` and responses `XResponse`.
- Use success codes in the form `<ENTITY>_<PAST_TENSE_VERB>` (`ITEM_CREATED`, `ITEMS_FETCHED`).
- Inject `validate` into every handler that reads a body, and tag every request field. Tag body UUIDs `required,uuid`.
- Detect duplicates with `*pgconn.PgError` code `23505` → `ErrXAlreadyExists` → 409.
- Return 413 for body-too-large.
- Keep the one JWT claims struct in `internal/auth`, with lowercase JSON tags, and read it via `auth.ClaimsFromContext`.
- Name every env key in `UPPER_SNAKE_CASE`.
- Run `go mod tidy` before committing, so direct deps aren't marked `// indirect` and unused modules are removed.
- Write table-driven, same-package tests with hand-written fakes and `httptest`. Assert on both the status and the response `code`.
- Run `sqlc generate` after any SQL change, and `gofmt` plus `go build ./... && go vet ./... && go test ./...` before handing off.

**Don't:**
- Don't edit `internal/database/db/`. It's generated.
- Don't put JSON or `validate` tags on domain or input structs.
- Don't write HTTP responses or status codes anywhere except `HandleError` and `WriteJSON`.
- Don't compare error strings. Use `errors.Is` / `errors.As`.
- Don't call `os.Getenv` outside `internal/config`.
- Don't add an ORM, DI framework, or assertion library.
- Don't let a service depend on another feature's service.
- Don't leave `fmt.Printf` debugging in handlers.
- Don't use `ON CONFLICT DO NOTHING` to detect duplicates.
- Don't declare a second claims struct.
- Don't use the `DTO` suffix.
- Don't add a `_SUCCESSFULLY` suffix to codes.
- Don't skip validation on any handler.
